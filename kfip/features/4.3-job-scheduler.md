## Summary

Let a module declare work that Koin runs **in the background**: once when the module is loaded (`onStart`), or repeatedly (`schedule`). Tasks are bound to the module lifecycle and to the Koin instance that loaded it.

```kotlin
val syncModule = module {
    single { SyncService(get()) }
    single(createdAtStart = true) { Cache() }

    onStart { get<Cache>().warmUp() }                              // once, in background
    schedule(every = 15.minutes) { get<SyncService>().refresh() }  // repeating
    onStart(Dispatchers.IO) { get<Db>().migrate() }                // blocking code → pick a dispatcher
}
```

---

## Motivation

Apps routinely need "prepare things in the background at startup" — warm a cache, prefetch, migrate, refresh periodically. Today this lives in `Application.onCreate` glue, ad-hoc `GlobalScope.launch`, or is (mis)done via `lazyModules`. Spring offered `@Scheduled` for the server side; Koin can provide a minimal, multiplatform equivalent built on coroutines, without a scheduler framework.

Koin already has the engine: `KoinCoroutinesEngine` (`koin-core-coroutines`) is a `CoroutineScope` with a `SupervisorJob`, a configurable dispatcher, cancellation on `close()`, and start jobs awaited by `waitAllStartJobs()`. It is only `@KoinInternalApi` today. This proposal exposes it through two module DSL verbs.

## Proposed Solution

### API (DSL in `koin-core-coroutines`)

```kotlin
fun Module.onStart(
    dispatcher: CoroutineDispatcher? = null,
    block: suspend Koin.() -> Unit,
)

fun Module.schedule(
    every: Duration,
    initialDelay: Duration = Duration.ZERO,
    dispatcher: CoroutineDispatcher? = null,
    block: suspend Koin.() -> Unit,
)
```

- The block is `suspend`, but **plain blocking code works**; blocking I/O should pass `Dispatchers.IO`. Coroutines are the mechanism, not a requirement for the user: they are the only background primitive available on all KMP targets (no threads on JS/Wasm).
- `schedule` is **fixed delay** (next run starts `every` after the previous one ends): runs never overlap.

### Naming

- `onStart` — "what to launch when Koin starts processing this module".
- `schedule` — deliberately close to Spring's `@Scheduled`.
- Rejected: `background`, `every`, `task`, `launch` (confusion with `CoroutineScope.launch`), `startJob`/`repeatJob` (leaks "job").

### `onStart` vs `createdAtStart`

| | `single(createdAtStart = true)` | `onStart { … }` |
|---|---|---|
| Purpose | **object**: create this instance at start | **action**: do something at start |
| When | synchronously, during `startKoin`, caller thread | asynchronously, after modules are loaded, engine dispatcher |
| Blocks start | yes | no (`waitAllStartJobs()` to wait) |
| Ready after `startKoin` | guaranteed | not guaranteed |
| Failure | fails fast at start | logged in background |

`onStart { get<X>() }` is **not** promoted as a background `createdAtStart`: a concurrent `get<X>()` from the main thread blocks on the singleton lock anyway, fail-fast is lost, and thread-confined objects (Android `Looper`, UI) break on `Dispatchers.Default`. Docs examples use actions (`warmUp()`, `refresh()`), not bare `get()`. If background eager creation proves necessary, it belongs on the definition, not in `onStart`.

### Coroutine context

Each Koin instance owns its engine (a `KoinExtension` in its own `extensionManager`), so each Koin owns its coroutine context:

- Default: `SupervisorJob() + Dispatchers.Default` (`KoinPlatformCoroutinesTools.defaultCoroutineDispatcher()`, all platforms).
- Added to the engine: a `CoroutineExceptionHandler` logging through `koin.logger` (an uncaught exception in `launch` would otherwise crash an Android app) and a `CoroutineName` per task (`koin-onStart`, `koin-schedule`) for debuggers and traces.
- Overrides: `coroutinesEngine(dispatcher)` for all tasks of that Koin, or `dispatcher =` per task.

### Lifecycle

The `Module` holds only task **declarations**. The engine of the Koin that loads the module launches them under a per-module `Job` (child of the engine `SupervisorJob`), keyed by module id. A shared `module { }` value loaded by several isolated `koinApplication { }` (typical in tests) therefore runs independently in each.

```
Koin A ── engine A (SupervisorJob A)
             └── syncModule → Job ── onStart, schedule
Koin B ── engine B (SupervisorJob B)
             └── syncModule → Job ── onStart, schedule
```

| Event | Effect |
|---|---|
| `startKoin { modules(m) }` | tasks start **after** all modules are loaded and `createdAtStart` instances exist |
| `loadKoinModules(m)` | `m`'s tasks start immediately |
| `unloadKoinModules(m)` | `m`'s job is cancelled (schedule loops + running onStart) |
| `stopKoin()` / `close()` | engine cancels everything (existing behavior) |
| module included several times | `flatten` dedupes, tasks run once |
| lazy module | tasks start when its background load completes |

`waitAllStartJobs()` awaits `onStart` tasks, **never** `schedule` tasks (they never complete).

## Drawbacks & Alternatives

- **New public API** (DSL + `onStart`/`schedule`) — additions only, `apiDump` required.
- **Hook in `koin-core`.** `Module` lives in `koin-core`, which has no coroutines dependency. Needs an internal task list on `Module` (stdlib types only: suspend lambda, `Duration`) and a start/stop callback from `Koin.loadModules` / `unloadModules`. Internal only.
- **Declared in `startKoin { }` instead of modules** — rejected: no unload story, worse organization.
- **Fixed rate / cron** — out of scope (overlap policy, timezone, missed runs).
- **Thread-based API** — rejected: not portable to JS/Wasm.

### Relation to lazy modules

`lazyModules` today moves two costs off the main thread: running module lambdas and indexing definitions. With the Koin Compiler Plugin making loading fast, and background preparation moving to `onStart`, **lazy modules are targeted for removal** (`lazyModule`, `lazyModules`, `LazyModule`), together with the `NoDefinitionFound` race they introduce when resolving before the background load completes.

Removal path (public API, so no removal in a minor):
1. 4.3: ship `onStart` / `schedule`, document them as the replacement for background preparation.
2. Deprecate `lazyModule` / `lazyModules` with `ReplaceWith` pointing to `module` / `modules`, once the compiler loading numbers are confirmed (DSL vs `lazyModules` vs compiler — start from `koin-core-coroutines` `module_400.kt` / `PerfsTest.kt`, `core/benchmark`).
3. Remove in the next major.

DSL-only users (no compiler plugin) lose background loading; the benchmark must show DSL loading cost is acceptable for them, or the deprecation message must point them to the compiler plugin.

## Implementation Notes

- Expose / reuse `KoinCoroutinesEngine`; auto-register it when a module with tasks is loaded (no silent "forgot `coroutinesEngine()`").
- Store running jobs in the engine (`moduleId → Job`), never on `Module`.
- Check `koinApplication { }` (non-global) behavior for eager instances and keep task start consistent with it.
- Tests with `runTest` virtual time + injected dispatcher: N runs in N periods, `waitAllStartJobs` excludes schedule, unload cancels only that module, close cancels all, failure in a schedule run is logged and the loop continues.
- `koin-core-coroutines` lacks a `wasmJs` target — add it.

## Open Questions

1. Failure in a `schedule` run: log and continue (proposed default) vs stop the task — or a parameter?
2. Should `onStart`/`schedule` return a handle (`Job`) for individual cancellation? (Not natural in a module DSL.)
3. Background eager creation on the definition (`createdAtStart` variant) — needed at all?
