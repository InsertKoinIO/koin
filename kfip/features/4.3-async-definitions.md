## Summary

Allow a definition to be built by a `suspend` function, and resolve it from a coroutine. The definition runs in the **caller's coroutine context** (dispatcher included): Koin does not pick a thread.

```kotlin
val appModule = module {
    single { Config("db://local") }
    coSingle { Database.open(get()) }          // suspend builder
    coSingle { Repository(await()) }              // async → async dependency
}

suspend fun load() {
    val repository = koin.await<Repository>()     // in a coroutine: suspends until created
}

fun onCreate() {
    val deferred = koin.getAsync<Repository>()    // plain code: returns a Deferred, runs in the Koin engine
}
```

---

## Motivation

Some dependencies can only be created by suspending code: opening a database, reading a configuration file, a network handshake, a token refresh. Today users either:

- block a thread inside a regular `single { runBlocking { ... } }` (deadlock-prone, forbidden on JS/Wasm), or
- inject a half-initialized object and add an `init()` suspend function called "somewhere", or
- wrap everything in `lazy`/`Deferred` by hand, re-implementing single-flight and retry.

Koin should offer the suspend creation path natively, with correct singleton semantics under concurrency.

### Prior art: Metro suspend providers

[Metro](https://zacsweers.github.io/metro/latest/coroutines/) (experimental, behind `enableSuspendProviders`) ships `suspend` `@Provides` functions:

- Suspension is computed **at compile time**: a binding is suspend if its provider is `suspend` or if it eagerly depends on a suspend binding. A non-suspend accessor to it is a compile error with the full path.
- Consumers can defer with `suspend () -> T`, `SuspendProvider<T>` or `SuspendLazy<T>`; `Provider<T>`/`Lazy<T>` over a suspend binding is rejected.
- **Execution context = caller.** Metro never switches dispatcher nor launches dependencies in parallel; providers do `withContext(IO)` themselves.
- Scoped values use `SuspendDoubleCheck`: volatile fast path, `Mutex` single-flight, failures/cancellations not cached, and a coroutine-context marker that fails fast on recursive self-requests instead of deadlocking.
- Out of scope: `Deferred<T>` injection, suspend `Set` multibindings, member injection, graph-owned `CoroutineScope`, resource disposal.

Koin resolves at runtime, so the compile-time propagation must become a **runtime contract** (see below). The singleton holder semantics transfer directly.

## Proposed Solution

### API (in `koin-core-coroutines`)

```kotlin
typealias SuspendDefinition<T> = suspend Scope.() -> T

// definitions
inline fun <reified T> Module.coSingle(qualifier: Qualifier? = null, noinline definition: SuspendDefinition<T>)
inline fun <reified T> Module.coFactory(qualifier: Qualifier? = null, noinline definition: SuspendDefinition<T>)

// resolution — already in a coroutine: suspends, runs in the caller's context
suspend inline fun <reified T> Scope.await(qualifier: Qualifier? = null): T
suspend inline fun <reified T> Koin.await(qualifier: Qualifier? = null): T

// resolution — from plain code: returns immediately, runs in the Koin coroutines engine
inline fun <reified T> Koin.getAsync(qualifier: Qualifier? = null): Deferred<T>
```

Inside a `coSingle` / `coFactory` builder, both `get()` (sync definitions) and `await()` (suspend definitions) are available.

### Naming decisions

Conventions in the Kotlin ecosystem drove the names:

| Convention | Used by | Koin |
|---|---|---|
| `co` prefix = coroutine flavour of an existing DSL verb | MockK (`coEvery`, `coVerify`), Spring (`router` → `coRouter`) | `coSingle`, `coFactory` |
| `await` = suspend until the result, called **from a coroutine** | kotlinx (`Deferred.await`, `awaitAll`), Spring WebFlux (`awaitBody`) | `await<T>()` |
| `Async` suffix = callable **from anywhere**, returns a handle | Java `supplyAsync`, kotlinx `async` | `getAsync<T>(): Deferred<T>` |
| no marker, the `suspend` keyword itself | Ktor, Room, Retrofit, Metro | `singleOf(::suspendFn)`, `@Single suspend fun` (see Future Considerations) |

Rejected:
- `singleAsync` / `asyncSingle` — `Async` wrongly suggests a future-returning call.
- `async single { }` (infix) — compiles, but an infix function takes a single argument: no qualifier, so a second syntax would be needed.
- `async { single { } }` block — works, but `async` reads like kotlinx `async` (eager, returns `Deferred`).
- Overloading `single { }` with a suspend lambda — **impossible**: Kotlin reports *overload resolution ambiguity* for a lambda literal (verified with Kotlin 2.4).
- A suspend `get()` — conflicts with the existing `get()` (a `suspend` modifier doesn't distinguish overloads, members win over extensions).
- `awaitLazy()` / suspend delegate — `await()` is already deferred and the single caches; Kotlin has no `suspend` `getValue`, so `by awaitInject()` cannot exist.

### Passing an async dependency to a sync definition

No `SuspendLazy`-like type is needed: hand over a plain `suspend () -> T` (what Metro recommends at injection sites too).

```kotlin
module {
    coSingle { Database.open(get()) }
    single { Repository(database = { await<Database>() }) }
}

class Repository(private val database: suspend () -> Database) {
    suspend fun load(id: String) = database().query(id)
}
```

### Singleton semantics (all platforms)

| Situation | Behavior |
|---|---|
| Already created | Lock-free read of a volatile field |
| Concurrent first callers | One creates (coroutine `Mutex`), others suspend and share the result |
| Builder throws | Not cached, next caller retries |
| Caller cancelled during creation | Not cached, next caller retries |
| A → B → A during creation | Fails fast: `Circular dependency …` (context marker, not a deadlock) |
| `null` result | Valid cached value |
| Created value | Not closed by Koin (no disposal contract yet) |

The cycle check follows structured child coroutines. Two **independent** coroutines that each create one async single and request the other can still deadlock (same documented limit as Metro).

### Execution context

The builder runs in the coroutine that calls `await()`. With `getAsync()`, there is no caller coroutine: it runs in the Koin coroutines engine (`SupervisorJob + Dispatchers.Default` by default, auto-registered if missing), see [Koin Job Scheduler](4.3-job-scheduler.md). To force a dispatcher, switch inside the definition:

```kotlin
coSingle { withContext(Dispatchers.IO) { Database.open(get()) } }
```

### Runtime contract (resolution semantics — compatibility event)

- `get<T>()` on a suspend definition must fail with an explicit error (`T is a suspend definition, use await()`), not a generic `NoDefinitionFound`.
- `await<T>()` on a regular definition: open question — accept (uniform suspend API, Metro allows `SuspendLazy` over sync bindings) or reject.
- Suspend definitions are only resolvable through `await()` / `getAsync()`; injected parameters / stacked params do not apply in the first iteration.

## Drawbacks & Alternatives

- **Runtime vs compile-time safety.** Without the compiler plugin, a misuse (`get()` on an async definition) is only caught at resolution time. The Koin compiler plugin could later reproduce Metro's static propagation check.
- **Coloring.** Any consumer of an async single eagerly is itself async. A plain `suspend () -> T` lambda is the escape hatch (see above).
- **`Deferred<T>` as the injected type** — rejected (as in Metro): exposes `cancel()` to every consumer, needs an owning scope, and caches failures. `getAsync()` returns a `Deferred` only as an entry point for plain code; definitions never receive one.
- **`createdAtStart` + `runBlocking`** — rejected: blocks a thread, impossible on JS/Wasm.
- **Dependency.** Requires kotlinx-coroutines, hence lives in `koin-core-coroutines`, not `koin-core`.

## Implementation Notes

### Sandbox (branch `new_async_schedule`)

- `core/koin-core-coroutines/src/commonMain/kotlin/org/koin/core/async/AsyncSingle.kt` — `AsyncInstance` holder interface, `AsyncFactory`, `AsyncSingle` (Mutex, volatile cache, `AsyncCreation` context marker).
- `core/koin-core-coroutines/src/commonMain/kotlin/org/koin/core/async/CoDefinitionExt.kt` — `coSingle`, `coFactory`, `await`, `getAsync`.
- `core/koin-core-coroutines/src/commonTest/kotlin/org/koin/core/async/CoDefinitionTest.kt` — 10 tests: created once, concurrent single-flight, caller context inheritance, retry after failure, async+sync dependencies, qualifiers, cycle fail-fast, `coFactory` per request, `coSingle`/`coFactory` coexistence, `getAsync` from plain code in engine context. Green on JVM, JS (node), macosArm64.

Mutation check (tests proven RED on broken code, JVM):

| Mutation in `AsyncSingle` | Caught by |
|---|---|
| no re-check inside the lock | `concurrent_callers_share_one_creation` |
| no cycle check | `recursive_request_fails_fast_instead_of_deadlocking` (deadlock → `runTest` 60s timeout) |
| failures cached as values | `failed_creation_is_not_cached` |

The sandbox stores `coSingle<T>` as a regular `single<AsyncInstance<T>>` with a synthetic qualifier: **not yet wired into the resolver**. Consequence: a `coSingle` and a `coFactory` of the same type and qualifier collide (override).

### Production path

- `ExtensionManager.extensions` is a plain `HashMap`: auto-registering the engine from concurrent `getAsync()` calls races — register it at start instead.
- Index suspend definitions under their real type with an "async" kind on `BeanDefinition`, so the resolver can emit the explicit error and tooling (Kotzilla, `verify()`) can see them.
- `koin-core-coroutines` has **no `wasmJs` target** while `koin-core` has one — must be added for this feature to be KMP-complete.
