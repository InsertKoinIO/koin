This page explains the ideas behind every other page, with one small example. It assumes you know [what dependency injection is](/docs/get-started/what-is-di/).

## The example

Three plain Kotlin classes. Each one receives what it needs in its constructor and knows nothing about Koin:

```kotlin
class ApiService

class UserRepository(private val api: ApiService)

class UserViewModel(private val repository: UserRepository) : ViewModel()
```

Koin's job is to create these objects and pass each one what it needs. It works in two steps:

## Declare your classes and start Koin

Here is the whole setup. The tabs show the same code in each style, and your choice is remembered on every page. Any tab works for now: [Choose your style](/docs/get-started/choose-your-style/) compares them.

<Tabs syncKey="koin-style">
<TabItem label="Compiler Plugin DSL">

```kotlin
import org.koin.core.context.startKoin
import org.koin.dsl.module
import org.koin.plugin.module.dsl.*

val appModule = module {
    single<ApiService>()
    single<UserRepository>()
    viewModel<UserViewModel>()
}

fun main() {
    startKoin {
        modules(appModule)
    }
}
```

These functions are stubs that the Koin Compiler Plugin replaces at build time, so apply the plugin to your Gradle module. See [Pick your platform](/docs/get-started/pick-your-platform/).

</TabItem>
<TabItem label="Annotations">

```kotlin
import org.koin.core.annotation.*
import org.koin.plugin.module.dsl.startKoin

@Singleton
class ApiService

@Singleton
class UserRepository(private val api: ApiService)

@KoinViewModel
class UserViewModel(private val repository: UserRepository) : ViewModel()

@Module
@ComponentScan("com.example.app")
class AppModule

@KoinApplication(modules = [AppModule::class])
class MyApp

fun main() {
    startKoin<MyApp>()
}
```

`@ComponentScan` collects every annotated class in the package `com.example.app` and its subpackages.

</TabItem>
<TabItem label="Constructor / Classic DSL">

```kotlin
import org.koin.core.context.startKoin
import org.koin.core.module.dsl.*
import org.koin.dsl.module

val appModule = module {
    singleOf(::ApiService)
    singleOf(::UserRepository)
    viewModelOf(::UserViewModel)
}

fun main() {
    startKoin {
        modules(appModule)
    }
}
```

The Classic DSL spells the same thing by hand: `single { UserRepository(get()) }`.

Three terms come from this code:

- A **definition** tells Koin how to create one type and how long to keep the instance. Koin reads the constructor of `UserRepository`, sees that it needs an `ApiService`, and gets it from the container. See [Definitions](/docs/concepts/definitions/).
- A **module** groups definitions, usually by feature or layer. It is only a description, and modules can include other modules. See [Modules](/docs/concepts/modules/).
- The **container** holds your definitions and the instances created so far. `startKoin` creates it, once, at the entry point of your app. On Android, call it in `Application.onCreate()` with `androidContext(this)`. `stopKoin()` closes it. See [Starting Koin](/docs/concepts/starting-koin/).

## Asking Koin for an object

An object gets its dependencies in one of two ways.

**Constructor injection** is the default: Koin passes each dependency when it creates the object. `UserRepository` and `UserViewModel` already work this way. The class stays plain Kotlin, and a test can call its constructor with fakes.

**Asking Koin** is for classes that a framework creates, such as an Android `Activity`, a Composable or a Ktor route. They call `get()` (now), `inject()` (on first access) or a ViewModel function:

```kotlin
import org.koin.androidx.viewmodel.ext.android.viewModel

class UserActivity : AppCompatActivity() {
    private val viewModel: UserViewModel by viewModel()
}
```

```kotlin
import org.koin.compose.viewmodel.koinViewModel

@Composable
fun UserScreen(viewModel: UserViewModel = koinViewModel()) {
    ...
}
```

This code is the same in every style. Ask only at these entry points, and let Koin build everything below them:

## Scope

A **scope** gives you one instance per open scope, released when you close it. Use it for an object tied to a user session, a screen or a request.

Say a `CartRepository` should exist only while a user is logged in. You declare it with `scoped<CartRepository>()` inside `scope<UserSession> { }`, or with `@Scope(UserSession::class)` and `@Scoped` on the class. Then you open and close the scope with the session:

```kotlin
// inside a KoinComponent
val sessionScope = getKoin().createScope<UserSession>("session-42")
val cart: CartRepository = sessionScope.get()

sessionScope.close() // releases CartRepository
```

A scoped definition can use definitions from the root container, and on Android, Koin provides ready-made scopes, so you rarely create one by hand. See [Scopes](/docs/concepts/scopes/) and [Android scopes](/docs/platforms/android/scopes/).

## Two definitions of one type

Koin finds a definition by its type. When two definitions provide the same type, a **qualifier** such as `@Named("auth")` tells them apart. See [Qualifiers](/docs/concepts/qualifiers/).

## Compile-time checks

If you remove `ApiService` from the module above, when do you find out?

- **With the [Koin Compiler Plugin](/docs/tooling/compiler-plugin/):** the build fails. The error starts like this, then names the class that needs it and the module:

  ```text
  [Koin][KOIN-D001] Missing dependency: com.example.app.ApiService
  ```

- **Without the plugin:** the code throws `NoDefinitionFoundException` when it runs. With the Constructor or Classic DSL, a unit test with `verify()` can find it earlier.

The plugin checks the full graph at each entry point (`startKoin`, `@KoinApplication`, Ktor's `install(Koin)`) and every `get()`, `inject()` or `koinViewModel()` call. See [Compile-time safety](/docs/tooling/compile-time-safety/) and [Diagnostics](/docs/reference/diagnostics/).
