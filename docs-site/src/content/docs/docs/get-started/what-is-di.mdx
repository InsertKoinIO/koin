Dependency injection (DI) means that a class **receives** the objects it needs, instead of creating them itself.

That is the whole idea. This page shows why it helps, using one small example. You don't need to know Koin to read it.

## What is a dependency?

A dependency is an object that another object needs to do its work. A car needs an engine to drive, so the engine is a dependency of the car.

## The problem

Here, `Car` creates its own engine:

```kotlin
class GasEngine {
    fun start() {
        println("Gas engine starting...")
    }
}

class Car {
    private val engine = GasEngine() // Car creates its engine

    fun drive() {
        engine.start()
        println("Car is driving")
    }
}
```

<DiDiagram name="creates" />

This works, but `Car` can only ever use a `GasEngine`:

- **It's hard to change.** To build an electric car, you have to edit the `Car` class.
- **It's hard to test.** Every test of `Car` runs a real engine. Imagine that the engine is a database or a network call: your tests become slow and unreliable.

## The solution

Give `Car` its engine through the constructor:

{/* check: what-is-di */}

```kotlin
interface Engine {
    fun start()
}

class GasEngine : Engine {
    override fun start() {
        println("Gas engine starting...")
    }
}

class ElectricEngine : Engine {
    override fun start() {
        println("Electric engine starting...")
    }
}

class Car(private val engine: Engine) { // Car receives its engine
    fun drive() {
        engine.start()
        println("Car is driving")
    }
}
```

<DiDiagram name="receives" />

`Car` no longer cares which engine it gets, so you can choose when you create it:

```kotlin
val gasCar = Car(GasEngine())
val electricCar = Car(ElectricEngine())
```

Testing also becomes easy, because you can pass a fake engine:

```kotlin
class FakeEngine : Engine {
    var started = false

    override fun start() {
        started = true
    }
}

@Test
fun driveStartsTheEngine() {
    val engine = FakeEngine()

    Car(engine).drive()

    assertTrue(engine.started)
}
```

This is dependency injection. You haven't used a library yet: it's only a constructor parameter.

## Why use a library?

In a small program, you can create everything by hand. In a real app, classes depend on classes that depend on other classes:

```kotlin
val database = Database()
val apiClient = ApiClient()
val userRepository = UserRepository(database, apiClient)
val userService = UserService(userRepository)
val viewModel = UserViewModel(userService)
```

<DiDiagram name="graph" />

You would have to write this code, keep it in the right order, and update it each time a constructor changes. You would also have to make sure that the whole app shares the same `Database`.

A DI library such as Koin does this work for you. You list your classes in a **module**, and Koin creates them in the right order and passes each one what it needs:

{/* check: what-is-di */}

```kotlin
import org.koin.core.context.startKoin
import org.koin.dsl.bind
import org.koin.dsl.module
import org.koin.plugin.module.dsl.single

val appModule = module {
    single<GasEngine>() bind Engine::class
    single<Car>()
}

fun main() {
    val koin = startKoin { modules(appModule) }.koin

    koin.get<Car>().drive()
}
```

<DiDiagram name="koin" />

You ask for a `Car`, and Koin builds the `GasEngine` and passes it in. `Car` itself doesn't change, and it doesn't know that Koin exists.

You don't need to run this code to follow this page. If you do, `single<T>()` requires the Koin Compiler Plugin: without it, the code fails with `NotImplementedError`. [Pick your platform](/docs/get-started/pick-your-platform/) leads to the install steps.

Koin has other ways to write this module, including annotations. [Choose your style](/docs/get-started/choose-your-style/) compares them.

## When a framework creates the class

You can't always use the constructor. Android creates each `Activity` itself, so you can't pass it parameters. In these classes, you ask Koin for what you need:

```kotlin
class UserActivity : AppCompatActivity() {
    private val viewModel: UserViewModel by viewModel() // ask Koin
}
```

Asking a shared registry for an object like this is called the **service locator** pattern. It is easy to confuse with DI, so here is the difference:

```kotlin
// Service locator: the class asks for what it needs.
// You can't see the dependency from outside, and tests need Koin.
class UserService : KoinComponent {
    private val repository: UserRepository by inject()
}

// Dependency injection: the class receives what it needs.
// The constructor shows the dependency, and tests can pass a fake.
class UserService(private val repository: UserRepository)
```

Follow this rule:

- **For your own classes,** such as repositories, services and ViewModels, use constructor parameters.
- **For classes a framework creates,** such as an `Activity`, a `Fragment` or a Ktor route, ask Koin.
