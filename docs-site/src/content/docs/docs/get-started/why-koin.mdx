The short answer:

- **Koin takes over the work of building your objects,** while your classes stay plain Kotlin.
- **It is the most widely used DI framework for Kotlin Multiplatform,** by every public measure we could find.
- **It is mature.** It has been developed in the open since 2017, under the Apache 2.0 license, with more than 200 contributors.

If dependency injection is new to you, read [What is dependency injection?](/docs/get-started/what-is-di/) first.

## What changes compared to no DI framework

You don't need a framework to apply dependency injection. Plain constructor parameters already do it. So the real question is: **who is in charge of your objects?**

<DiDiagram name="ownership" />

Say `UserRepository` now needs a `Logger`. Without a framework, you create the `Logger` and update every place that builds a `UserRepository`, in your Android app, your iOS entry point and your tests:

```kotlin
val database = Database()
val apiClient = ApiClient()
val logger = Logger() // new
val userRepository = UserRepository(database, apiClient, logger) // changed
```

With Koin, you add `logger` to the constructor and declare `Logger`. The rest doesn't change:

```kotlin
val appModule = module {
    single<Database>()
    single<ApiClient>()
    single<Logger>() // new
    single<UserRepository>() // unchanged
}
```

| | No framework | Koin |
|---|---|---|
| **Creating objects** | You call each constructor, in order | Koin works out the order |
| **New dependency** | Update each place that builds the class | Change the constructor |
| **Tied to a screen or session** | You store and clean up | [`scoped`](/docs/concepts/scopes/) |
| **Several platforms** | Share your own container, or repeat per app | One graph in `commonMain`, plus a [platform module](/docs/platforms/kmp/platform-dependencies/) |
| **Missing dependency** | Build error | Build error with the [Compiler Plugin](/docs/tooling/compiler-plugin/), otherwise at runtime |

Unit tests don't change: you still pass a fake. Your classes also stay free of Koin, apart from [annotations](/docs/get-started/choose-your-style/) if you choose that style, so adopting Koin doesn't lock your business logic in.

:::tip[When you don't need Koin]
For a small app with a handful of classes, plain constructors are enough. Keep using them: they make moving to Koin easy later, if your app grows.
:::

## The most used DI framework in Kotlin Multiplatform

You declare your graph once in `commonMain`, and your apps start it from a [single function](/docs/platforms/kmp/start-koin/). It needs no generated sources and no per-target configuration. ViewModels and Compose work from shared code, and `koin-core` runs on every Kotlin target.

| | klibs.io dependents | KMP build files |
|---|---|---|
| **Koin** | **146** | **765** |
| Metro | 11 | 277 |
| kotlin-inject | 10 | 79 |
| Kodein | 11 | 49 |

Measured on November 2, 2026.

<details>
<summary>How to read these numbers</summary>

- **klibs.io dependents** is the count shown on each project's [klibs.io](https://klibs.io/project/InsertKoinIO/koin) page, the JetBrains catalog of multiplatform libraries.
- **KMP build files** is the number of public `build.gradle.kts` files on GitHub that mention both the library and `commonMain`, from GitHub code search. Treat it as an estimate.
- **Private projects aren't counted,** so none of these measure the whole market. Metro is also much newer than the others: its repository dates from late 2024.
- **We found no independent survey** that ranks DI frameworks for Kotlin Multiplatform. These public signals are the best evidence available.

</details>

The Kotlin documentation calls Koin "[a reliable multiplatform DI framework](https://kotlinlang.org/docs/multiplatform/migrate-from-android.html)", and that migration guide moves a real app from Dagger and Hilt to Koin. The official [KMP App Template](https://github.com/Kotlin/KMP-App-Template) and [production sample](https://github.com/Kotlin/kmp-production-sample) use Koin too. The same documentation also presents [Metro as an option](https://kotlinlang.org/docs/multiplatform/compose-viewmodel.html), and the [KotlinConf app](https://github.com/JetBrains/kotlinconf-app/pull/581) moved its client from Koin to Metro in 2026, while its backend still uses Koin.

## What the runtime model gives and costs

Koin keeps your graph in a container at runtime, and runs a Kotlin function for each definition, with no reflection. The [Koin Compiler Plugin](/docs/tooling/compiler-plugin/) adds checks at build time. [Core concepts](/docs/get-started/core-concepts/) shows how the two parts fit.

| What it gives | What it costs |
|---|---|
| **Dynamic modules:** load and unload modules after start, for feature flags or on-demand features. See [Starting Koin](/docs/concepts/starting-koin/). | **Startup work:** modules are registered when Koin starts, every lookup goes through the container, and `createdAtStart` definitions run on the thread that starts Koin. |
| **Lazy modules:** load part of the graph in the background to reduce startup work. See [Lazy modules](/docs/concepts/lazy-modules/). | **Runtime errors without the plugin:** with the Constructor or Classic DSL and no plugin, a missing definition is found when the code runs, or in a [`verify()`](/docs/testing/verify/) test. |
| **Runtime scopes:** open and close scopes for a session, a screen or a request. See [Scopes](/docs/concepts/scopes/). | **Limits of the checks:** modules loaded with `loadKoinModules()` can't be proven at build time, and a library module is only checked when an app assembles it. See [Compile-time safety](/docs/tooling/compile-time-safety/). |
| **No generated sources:** nothing to commit, nothing to configure per Kotlin Multiplatform target. | **Kotlin version coupling:** each Compiler Plugin release is verified on a list of Kotlin versions. See [Compiler Plugin](/docs/tooling/compiler-plugin/). |

## When another tool fits

Koin is not the right choice for every project. DI libraries differ mainly in when they do their work:

<DiDiagram name="landscape" />

Consider another option when:

- **You want no runtime container at all.** Metro and kotlin-inject resolve the graph at build time. Metro is multiplatform and built as a compiler plugin, like Koin's checks. You give up the dynamic features above.
- **Your app is Android only and already uses Hilt.** Hilt is the DI library recommended in the Android documentation, and you may not need to change. If you are weighing a move, see [Koin vs Hilt](/docs/migration/koin-vs-hilt/).
- **Your app has a very strict startup budget.** Measure the startup costs listed above on your own app.
- **You must stay on a Kotlin version the Compiler Plugin doesn't support.** The Constructor and Classic DSL still work without it, with runtime checks only.
